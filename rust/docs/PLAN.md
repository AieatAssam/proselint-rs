# Migration scope

The migration advances capability by capability against the pinned Python baseline. Each accepted capability has focused cases derived from upstream behavior, passing Rust tests, a live comparison, an independent verification, and recorded evidence.

The goal is compatibility across the inventoried checks and required CLI behavior. Until every required capability passes the cumulative live gate, this project is a partial port. Current coverage and open areas are listed in [`PROGRESS.md`](PROGRESS.md); behavioral details are tracked in [`COMPATIBILITY.md`](COMPATIBILITY.md).

## Implementation roadmap

The pinned inventory contains 106 unique check paths. The current accepted set has 37 rule paths and two bounded CLI capabilities, leaving 69 rule paths to implement and verify. Preserve duplicate registrations as separate checks even when they share a path. The order below reduces repeated work by establishing shared semantics before adding large data sets.

1. **Finish shared matching and CLI behavior.** Match Fast/RE2 case folding, word-boundary activation followed by raw match iteration, message/replacement lookup, `max_errors` truncation order, file URI encoding, structured JSON errors, and per-file check selection. Keep negative tests for Unicode folds that Python `re` accepts but RE2 does not.
2. **Build out common check types.** Add reusable behavior for `Existence`, `ExistenceSimple`, and `PreferredFormsSimple`, including padding, quote policy, case handling, offsets, duplicate output, source ordering, and exact null/replacement fields. These types account for most registered checks. Use live probes before sharing a matcher across rule families.
3. **Port data-backed rules in small groups.** Start with literal existence and preferred-form families: archaism and clichés; industrial language; capitalization and malapropisms; idioms and phrase lists; spelling and terminology; social-awareness and redundancy lists. Keep one acceptance record per check path and preserve batch boundaries and registration order. Record the pinned source and verify redistribution terms before including sourced word lists.
4. **Add regex and specialized check types.** Cover ordinary Fast regex checks, then `Consistency`, `ReverseExistence`, custom PPM behavior, and Fancy/Python-regex rules. Fancy patterns include lookarounds and backreferences; select an engine only after differential probes establish its behavior for spans, ordering, and resource use.
5. **Complete the CLI contract.** Add default configuration and combined checks, config discovery and precedence, all output formats, file and directory input, multiple files, decoding and newline behavior, and remaining error/argument paths. Verify default-enabled and default-disabled rules separately; a selected-rule pass does not establish default behavior.
6. **Run the full compatibility gate before broad benchmarking.** The existing benchmark measures one accepted rule on three workloads. Broaden benchmark coverage only after the measured configs and inputs pass exact live parity; label each corpus and generated stress workload separately, and report raw samples and environment with the results.

Progress should be measured by accepted unique check paths, registered entries exercised, and live cases passed. Do not count cached snapshots or unimplemented paths toward compatibility.

## Public-domain book benchmark

Add a separate end-to-end corpus benchmark using only full texts whose public-domain status and redistribution terms have been verified for the project's intended jurisdiction. Prefer well-regarded prose and deliberately awkward or error-rich writing where suitable examples are available. Select candidates using transparent, recorded measures (for example, review/rating source and date), and retain the selection rationale rather than treating subjective labels as fact. Where practical, discover candidates dynamically from Project Gutenberg's downloadable machine-readable catalog rather than scraping its website; Gutenberg explicitly provides catalog data for programmatic use and asks automated clients to use those data instead of crawling pages ([catalog access guidance](https://www.gutenberg.org/ebooks/offline_catalogs.html), [robot access policy](https://www.gutenberg.org/policy/robot_access.html)).

Treat Project Gutenberg's rights classification as a candidate filter and cite the classification in the corpus manifest. Gutenberg says its copyright clearance establishes status under U.S. law only, allows a small number of works distributed with permission, and warns that other countries may differ ([copyright rules](https://www.gutenberg.org/help/copyright.html), [terms of use](https://www.gutenberg.org/policy/terms_of_use.html)). Therefore admit only entries explicitly identified as public domain in the United States, exclude permission-based copyrighted works, retain each ebook's rights notice and catalog record, and verify the intended jurisdiction separately before redistributing texts there. Gutenberg metadata may omit the original print publication dates, so a catalog match alone is not sufficient to establish the status of a specific edition.

For each selected book, record the authoritative source URL, author, edition/transcription details, publication date, rights basis, source license/terms, and SHA-256 of the exact downloaded text. Do not include a text unless its public-domain status is established; do not assume that an online copy or a public-domain earlier edition makes a later transcription, introduction, or annotation public domain. Keep the full source and any derived pages under the documented license/attribution terms.

Normalize each text with a documented, deterministic procedure, then split it into stable numbered pages with a recorded page size and per-page hashes. Run the pinned Python executable and Rust implementation side by side on identical page bytes, configuration, checks, output format, and error limit. First compare every page's diagnostics and exit status exactly; collect speed measurements only for parity-passing inputs. Use paired, interleaved repeated samples, separating fresh-process CLI time from sustained in-process scanning, and report raw samples, medians, spread, environment, commands, corpus metadata, and hashes. Include both corpus-wide totals and per-book/page results so density, size, and speed differences remain inspectable. Add generated high-density inputs as a distinct stress class, never as substitutes for real-book results.

Ray Bradbury's “Dark They Were, and Golden-Eyed” and Daniel Keyes's short-story version of “Flowers for Algernon” are suggested writing contrasts, but their 1950 and 1959 publication dates make them unsuitable for a public-domain-only corpus absent specific evidence establishing public-domain status for the exact text. Exclude them unless that rights check supports inclusion; the novel version of “Flowers for Algernon” is outside the proposal regardless. Public-domain candidates should be selected and verified independently of the desired benchmark outcome.
